# Approach write-up

**What I prioritised.** The brief weights AI integration and architecture highest, so I built the backend and its tests first and the UI last. The rule I held throughout: the AI assists but never acts. It suggests a category, a priority and a draft, and every reply goes out only after an admin edits and sends it.

**Key architecture choices.** A layered FastAPI service (thin routes, services holding the rules, an `ai/` package with no web or database dependencies) and MongoDB. Security is structural rather than careful: every author query carries the author's identity inside the filter, so another author's data simply isn't found (404, not 403); internal notes and public replies are separated by a field and read through one function that hard-codes "public"; the AI's recommendation is stored apart from the admin's final value, so an override can't be silently overwritten, even by an AI call that finishes late. Real-time uses WebSocket events that carry only identifiers, so the client refetches through the authorised REST API and a broadcast bug can't leak content.

**How the AI is integrated.** One triage call (category + priority, JSON, validated, one repair retry) runs in the background after a ticket is saved. Drafting runs on demand, with only the ticket, its book record, the last few public replies and the knowledge-base sections for that category, which keeps prompts near 730 tokens for triage and 1,400 for drafts. Facts the model might get wrong (dates, overdue-ness, money) are computed in code and handed over as labelled data; the prompt forbids inventing actions, and deterministic checks warn the admin about unknown amounts, placeholders, claims of completed actions and payment promises.

**How failure is handled.** Tickets are created before any AI call. If the AI is down, rate-limited, unconfigured or returns junk, the ticket is flagged "AI failed: set manually", the draft button shows a clear message with the manual editor still open, and no provider detail reaches the client. This is covered by automated tests with a fake provider.

**Evidence.** I labelled 28 realistic tickets on the supplied dataset, including injection, Hinglish and vague cases, and measured the real model: category in the accepted set on 28/28 (95% interval 88–100%), priority in range on 26/28, all 10 urgent tickets caught, none under-triaged. The weaknesses are stated, not hidden: a missing payout-threshold rule in the triage prompt, uninformative model confidence (so the UI doesn't show it), small sample, and labels written by the prompt's author.

**Trade-offs.** In-process background tasks and an in-memory WebSocket hub instead of a queue and Redis; JWT in localStorage instead of cookies; no author replies, attachments or email notifications; no frontend test suite. All are listed in the README.

**Toward production.** A durable job queue with retries; Redis pub/sub for multiple workers; httpOnly cookies, refresh tokens and revocation; login rate limiting; audit and AI-cost dashboards; a larger independently labelled evaluation run on every prompt change; escalation to the production team as an actual workflow; and email notifications.
